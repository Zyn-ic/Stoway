## Project Overview

Stoway is a Roblox inventory framework. The core is a pure Luau inventory engine called `CoreStore` — no Roblox types, no UI, no networking. It lives inside an orchestration layer called `StowayServerV3_0_0` that connects it to Roblox-specific systems.

**CoreStore lives at:** `ReplicatedStorage/Shared/Stoway/CoreStore/` (canonical, pure Luau, no Instances)

**Client mirror (light):** `src/client/StowayClientV3/CoreStore/` — re-exports Types + pure Query/State for Fusion views (see below)

**Orchestration layer:** `src/server/Services/StowayServerV3_0_0/init.luau` (requires `ReplicatedStorage.Shared.Stoway.CoreStore` at runtime)

**Communications adapter:** `src/server/Services/StowayServerV3_0_0/Communications.luau`

**Client (StowayClientV3, branch `client`):** `src/client/StowayClientV3/` — Fusion 0.3 (`isRelease=true`, Studio `Workspace.Fusion` snapshot, `UsedAs`/`Graph`/`lazy For`) client. Mapped to `StarterPlayer.StarterPlayerScripts` via `default.project.json`. Boots from the server snapshot; settings-driven hotbar + sectioned storage, drag + drop, multi-platform input (PC/console/touch), skin hooks. Structured around the master plan's `HotbarType` vs `UiSkin` split: `CoreStore/` (pure state+query), `Controller/` (Fusion RootScope + `LayoutManager`), `Layouts/<HotbarType>/` (render engines), `Skins/<SkinName>/` (GUI prefab loaders + code-built skins), `Slot/SlotView.luau` (shared across layouts). Scopes are `Fusion.Scope<typeof(Fusion)>` (see Fusion notes below). See `src/client/StowayClientV3/README.md`.

**Shared (Stoway):** `ReplicatedStorage/Shared/Stoway/` — shared types, settings defaults, colors, Result type, StowayRemotes wire, **CoreStore** (see below).

**Vendored Fusion:** `ReplicatedStorage/Packages/fusion/` (Fusion 0.3 `isRelease=true`, copied from Studio `Workspace.Fusion` snapshot; `UsedAs` + `Graph`/`evaluate`/`change` + `lazy For` + `State/For/init.lua` with `Disassembly`/`ForTypes`; do NOT wally install again or the root `Packages/` folder will reappear. `wally.toml` still pins `acecateer/fusion@0.3.1` for reference only).

**Skin prefabs (Studio-only, NOT in the repo):** `ReplicatedStorage/Stoway/GUI/<SkinName>/` (flat — exactly one ScreenGui directly under the skin folder, plus `Slot/`) — ScreenGui holds Hotbar/Backpack frames + BackpackStuff, `Slot/template` slot prefab (slotbutton, stackcount, slotnumber, selecticon, rarityframe). One shared `GUI/DraggingGui` for the drag ghost. Optional `Slot`-folder attributes: `GhostHidden` / `HideInStorage` / `HideInHotbar` (comma names), `SlotBleedPx` (number). The GUI lives in the .rbxl only; a `rojo build` output has no GUI and the client warns + skips views.

**Code-built skins (in the repo, no prefab):** `Skins/Jailbreak` and `Skins/Persona` build their GUI in Lua and return the same `SkinHandle` shape as the prefab loader. `Skins/Persona` is the slanted-ink look (6-degree tilt, white miter outlines, red accent `235,35,55`, combo-counter font) and pairs with the `JailbreakHotbar` layout; it ships its own hook table (`Persona/Hooks.luau`) plus a TweenService-only FX runtime (`Persona/Fx.luau`), so the skin visuals ride the 11 skin hooks without a `HookFuncs` prefab folder.

## Type Checking

Type checking is the standing gate. Run from the repo root to type-check
everything except vendored packages (`rojo serve` keeps `sourcemap.json`
fresh via `--watch` — do NOT regenerate it by hand, just point the analyzer
at the root copy):

```
luau-lsp analyze --definitions="globalTypes.d.luau" --sourcemap="sourcemap.json" --ignore="**/Packages/**" src
```

- Download Roblox definitions once from
  `https://raw.githubusercontent.com/JohnnyMorganz/luau-lsp/main/scripts/globalTypes.d.luau`
- `sourcemap.json` at the project root is autogenerated (`rojo sourcemap --watch` / `rojo serve`). Zed `luau-lsp` `sourcemap.autogenerate:true` `rojoProjectFile:"default.project.json"` `sourcemapFile:"sourcemap.json"` uses it.
- Expected result: **0 errors** outside `ReplicatedStorage/Packages/**` with the old solver (`LuauSolverV2=false`, `rokit` default). With Zed `fflags > enable_new_solver:true` (`LuauSolverV2=true`) you will see `Value`/`Computed` `nil | T` vs `T` noise on `ClientStore`/`SlotView` — add explicit `:: Fusion.Value<T>` / `:: Fusion.Computed<T>` or `function(use: Fusion.Use): string?` to silence, or set `enable_new_solver:false` to match CI.
- In Studio, the luau-lsp VS Code extension resolves requires via Rojo sourcemap + `.luaurc`.

### Replication default

`replicate` is opt-in on every Stoway operation route: `nil` (omitted) means **no** replication; pass `true` to echo a server-side change to a client. Passing `false` is equivalent to omitting it.

## Require System

All modules use **static Instance-path requires** — one require, no pcall/alias fallbacks.
This is required for luau-lsp: a dual `pcall(instance-path)` + `require("@alias")` shim makes
the binding a union type, and `Types.InventoryState`-style type member access on a union
always fails ("Unknown type"). The repo targets Studio + Roblox definitions only.

**Usage in modules:**

```luau
local ReplicatedStorage = game:GetService("ReplicatedStorage")
local Types = require(ReplicatedStorage.Shared.Stoway.CoreStore.Types)
```

Within a service folder, children resolve via `script`:

```luau
local Protocol = require(script.Parent.Protocol) -- sibling module
local Protocol = require(script.Protocol)        -- child of an init.luau folder-module
```

`.luaurc` aliases are still configured for the luau-lsp extension but production code does
not use them at runtime.

**Do NOT use:**
- Relative paths like `require("../CoreStore/Types")` — break in luau-lsp Roblox mode
- Alias requires (`require("@CoreStore/...")`) in production code — they throw at Studio runtime
- Dual pcall require shims — they poison types (union) for the analyzer

### Key State Shape

```luau
InventoryState = {
    Items: { [string]: Item },           -- O(1): UUID -> Item
    ItemsByID: { [string]: { string } }, -- O(1): ItemId -> UUIDs
    Hotbar: { string? },                 -- 1..MaxHotbarSlots, Static has holes
    Storage: { string },                 -- packed array, no holes
    LocationByUUID: { [string]: SlotRef }, -- O(1): UUID -> where
    MetadataIndex: { [string]: { [string]: { string } } }, -- O(1): field -> value -> UUIDs
    EquippedItemUUID: string?,
    Weight: number,
    Settings: Settings,
}
```

### Settings Defaults

```luau
HotbarType = "Static"     -- or "Dynamic"
MaxHotbarSlots = 10
Limit = 15                -- 0 = infinite
CanStack = true           -- merge into existing stacks; new stacks still cap
MaxStackSize = 5
BackpackEnabled = true
StackOnSwap = false       -- system-level, default off
Sorting = false
SortOrder = "None"        -- "None" | "Name" | "Rarity" | "ItemType"
StackRequiredFields = { "Rarity", "Type" }
StackBlacklist = { Legendary = true, Mythic = true, Special = true }
```

### Operations Summary

| Operation | What it does | Complexity |
|-----------|-------------|------------|
| add | Add item(s), stack into existing or create new | O(k) stack, O(1) new |
| remove | Partial or full removal | O(1) partial, O(h)/O(n) full |
| swap | Exchange two slot positions. StackOnSwap can absorb | O(1) same-container, O(n) cross-container |
| swapStack | Explicit stack route; follows swap's StackOnSwap behavior | Same as swap |
| move | Positional transfer, never stacks | O(1) HH, O(h) HS, O(n) SH/SS |
| split | Divide stack, cap at MaxStackSize | O(1) + placement |
| updateMetadata | Merge key-value pairs, all mutable | O(f) |
| sort | Auto-triggered, sorts Storage only | O(n log n) |

### Key Behaviors

- **Stacking:** `add` merges into existing stacks when `CanStack = true`; `swap`/`swapStack` merge only when `CanStack` and `StackOnSwap` are both true. Move and split never merge. New stacks from `add` always cap at `MaxStackSize`.
- **MaxStackSize:** Enforced unconditionally. No item Amount may exceed it after any operation.
- **Dynamic hotbar:** Compacts after remove/swap/move. Static preserves holes. Use `CoreStore.setHotbarType(state, "Dynamic")` to switch types — it auto-compacts.
- **Auto-sort:** Triggers after any mutating operation when `Sorting = true`. Sorts Storage only. Hotbar is never sorted (user-controlled).
- **MetadataIndex:** Indexed fields: Rarity, Type. O(1) bucket lookups for find().
- **Settings replication:** engine settings push sparsely per change (`SettingsChanged`); `FullSync` carries the full snapshot as backstop. Client overlays onto `_state`, never atoms directly.
- **Optimistic ops + revert:** client applies drags locally; server rejects arrive as revert + FullSync (no silent forks). Revert is log-only — never re-request (no triple-send). Boot always requests one snapshot; the server's per-player 15s throttle absorbs races with the join push.
- **Single-sync:** op bodies (`swapOp` etc.) sync atoms on success; signal handlers never sync twice.
- **Ghost healing:** an `Added` push for an occupied hotbar slot whose occupant has no item entry is evicted, not skipped. Real-item conflicts still warn + skip.

## Common Pitfalls

1. **`table.clone` not `Utils.deepCopy`** for flat settings tables — `deepCopy` is for nested item metadata.
2. **`split` always caps at MaxStackSize** regardless of CanStack — this is intentional.
3. **Move never stacks** — use `swap` or `swapStack` with `StackOnSwap = true` if you want to merge.
4. **Static hotbar preserves holes** — `compactHotbar` is a no-op. Only Dynamic compacts.
5. **Sort is descending for rarity** — Special > Mythic > Legendary > ... > Common.
6. **`StackOnSwap` does NOT stack during move** — it applies to swap and swapStack only. This is a common misconception.
7. **Nil values in `updateMetadata`** — In Luau, `{ Key = nil }` creates empty table. Nil values are silently ignored. To delete a key, use the `CoreStore.METADATA_DELETE` sentinel.
8. **MetadataIndex maintenance** — every `createItem`, `destroyUnplacedItem`, `remove`, and `updateMetadata` must update MetadataIndex.
9. **Dynamic Hotbar slot availability** — The only available slot is the append position (`findEmptyHotbarSlot`). Operations targeting non-append slots are rejected with `DESTINATION_UNAVAILABLE`. Preferred slot is ignored in Dynamic mode. Use `CoreStore.setHotbarType(state, "Dynamic")` to switch types — it auto-compacts the hotbar.
10. **`Fusion.Scope<any>` has no `Hydrate`/`ForPairs`** — `Types.Scope<Constructors> = {Task} & Constructors`, so `Scope<any>` is `any & {Task}` with no Fusion members. Use `Fusion.Scope<typeof(Fusion)>` (as in `HotbarView`, `StorageView`, `SlotView`, `LayoutManager`, `PointerDragService`). Zed `enable_new_solver:true` surfaces this.
11. **Lazy `For` side-effects need `Observer`** — Studio `Fusion` `For` is `timeliness="lazy"`. `scope:ForPairs` that only does `SlotView.Create` + `Parent = hotbarFrame` and ignores the returned table never runs unless observed. Wrap side-effect `For`s with `local f = scope:ForPairs(...); Fusion.peek(f); scope:Observer(f)` as in `HotbarView`/`StorageView`. The 0.3.1 `For` was eager via `updateAll`.
12. **No live property reads as `Computed` fallbacks** — `return slotnumber.TextColor3` inside the `Computed` bound TO `slotnumber.TextColor3` self-perpetuates (once amber, amber forever). Capture once (`local default = inst.Prop`) and return the capture. The codebase already does this (`originalPosition`, `origSize`).
13. **Pushed settings go through `_state` first** — writing atoms directly gets clobbered by the next op's `sync()`. Funnel: `ClientController.ApplyServerSettings` (overlay onto `_state`, then `sync()` fans out). Same for any future pushed state.
14. **`CanStack = false` is not `MaxStackSize = 1`** — it only blocks merging into existing stacks. `add apple 5` still creates one stack of 5. Set `MaxStackSize = 1` for one item per unit.
