## Project Overview

Stoway is a Roblox inventory framework. The core is a pure Luau inventory engine called `CoreStore` — no Roblox types, no UI, no networking. It lives inside an orchestration layer called `StowayServerV3_0_0` that connects it to Roblox-specific systems.

**CoreStore lives at:** `ReplicatedStorage/Shared/Stoway/CoreStore/` (canonical, pure Luau, no Instances)

**Client mirror (light):** `src/client/StowayClientV3/CoreStore/` — re-exports Types + pure Query/State for Fusion views (see below)

**Orchestration layer:** `src/server/Services/StowayServerV3_0_0/init.luau` (requires `ReplicatedStorage.Shared.Stoway.CoreStore` at runtime)

**Communications adapter:** `src/server/Services/StowayServerV3_0_0/Communications.luau`

**Client (StowayClientV3, branch `client`):** `src/client/StowayClientV3/` — Fusion 0.3 (`isRelease=true`, Studio `Workspace.Fusion` snapshot, `UsedAs`/`Graph`/`lazy For`) client. Mapped to `StarterPlayer.StarterPlayerScripts` via `default.project.json`. Boots from the server snapshot; settings-driven hotbar + sectioned storage, drag + drop, multi-platform input (PC/console/touch), skin hooks. Structured around the master plan's `HotbarType` vs `UiSkin` split: `CoreStore/` (pure state+query), `Controller/` (Fusion RootScope + `LayoutManager`), `Layouts/<HotbarType>/` (render engines), `Skins/<SkinName>/` (GUI prefab loaders), `Slot/SlotView.luau` (shared across layouts). Scopes are `Fusion.Scope<typeof(Fusion)>` (see Fusion notes below). See `src/client/StowayClientV3/README.md`.

**Shared (Stoway):** `ReplicatedStorage/Shared/Stoway/` — shared types, settings defaults, colors, Result type, StowayRemotes wire, **CoreStore** (see below).

**Vendored Fusion:** `ReplicatedStorage/Packages/fusion/` (Fusion 0.3 `isRelease=true`, copied from Studio `Workspace.Fusion` snapshot; `UsedAs` + `Graph`/`evaluate`/`change` + `lazy For` + `State/For/init.lua` with `Disassembly`/`ForTypes`; do NOT wally install again or the root `Packages/` folder will reappear. `wally.toml` still pins `acecateer/fusion@0.3.1` for reference only).

**Skin prefabs (Studio-only, NOT in the repo):** `ReplicatedStorage/Stoway/GUI/<SkinName>/` (flat — exactly one ScreenGui directly under the skin folder, plus `Slot/`) — ScreenGui holds Hotbar/Backpack frames + BackpackStuff, `Slot/template` slot prefab (slotbutton, stackcount, slotnumber, selecticon, rarityframe). One shared `GUI/DraggingGui` for the drag ghost. Optional `Slot`-folder attributes: `GhostHidden` / `HideInStorage` / `HideInHotbar` (comma names), `SlotBleedPx` (number). The GUI lives in the .rbxl only; a `rojo build` output has no GUI and the client warns + skips views.

## Require System

All modules use **static Instance-path requires** — one require, no pcall/alias fallbacks.
This is required for luau-lsp: a dual `pcall(instance-path)` + `require("@alias")` shim makes
the binding a union type, and `Types.InventoryState`-style type member access on a union
always fails ("Unknown type"). The repo targets Studio + Roblox definitions only.

**Usage in modules:**

```luau
local ReplicatedStorage = game:GetService("ReplicatedStorage")
local Types = require(ReplicatedStorage.Shared.Stoway.CoreStore.Types)
```

Within a service folder, children resolve via `script`:

```luau
local Protocol = require(script.Parent.Protocol) -- sibling module
local Protocol = require(script.Protocol)        -- child of an init.luau folder-module
```

`.luaurc` aliases are still configured for the luau-lsp extension but production code does
not use them at runtime.

**Do NOT use:**
- Relative paths like `require("../CoreStore/Types")` — break in luau-lsp Roblox mode
- Alias requires (`require("@CoreStore/...")`) in production code — they throw at Studio runtime
- Dual pcall require shims — they poison types (union) for the analyzer

### Operations Summary

| Operation | What it does | Complexity |
|-----------|-------------|------------|
| add | Add item(s), stack into existing or create new | O(k) stack, O(1) new |
| remove | Partial or full removal | O(1) partial, O(h)/O(n) full |
| swap | Exchange two slot positions. StackOnSwap can absorb | O(1) same-container, O(n) cross-container |
| swapStack | Explicit stack route; follows swap's StackOnSwap behavior | Same as swap |
| move | Positional transfer, never stacks | O(1) HH, O(h) HS, O(n) SH/SS |
| split | Divide stack, cap at MaxStackSize | O(1) + placement |
| updateMetadata | Merge key-value pairs, all mutable | O(f) |
| sort | Auto-triggered, sorts Storage only | O(n log n) |

### Key Behaviors

- **Stacking:** Only via `add` (always), `swap`, or `swapStack` when `StackOnSwap = true`. Move and split never stack.
- **MaxStackSize:** Enforced unconditionally. No item Amount may exceed it after any operation.
- **Dynamic hotbar:** Compacts after remove/swap/move. Static preserves holes. Use `CoreStore.setHotbarType(state, "Dynamic")` to switch types — it auto-compacts.
- **Auto-sort:** Triggers after any mutating operation when `Sorting = true`. Sorts Storage only. Hotbar is never sorted (user-controlled).
- **MetadataIndex:** Indexed fields: Rarity, Type. O(1) bucket lookups for find().
- **Settings replication:** engine settings push sparsely per change (`SettingsChanged`); `FullSync` carries the full snapshot as backstop. Client overlays onto `_state`, never atoms directly.
- **Optimistic ops + revert:** client applies drags locally; server rejects arrive as revert + resync (no silent forks).
- **Ghost healing:** an `Added` push for an occupied hotbar slot whose occupant has no item entry is evicted, not skipped. Real-item conflicts still warn + skip.
- **Cooldowns (this branch):** see [Cooldown Metadata Showcase](#cooldown-metadata-showcase-this-branch).

### Cooldown Metadata Showcase (this branch)

Skill cooldowns with zero engine changes — three metadata keys, server
authority, client veils. Canon engine behavior above is untouched.

| Key | Writer | Meaning |
|-----|--------|---------|
| `Cooldown` | designer / `cooldown-demo` | duration, seconds |
| `FireOnEquip` | designer / `cooldown-demo` | `true` = kind-A (fire on equip); else kind-B (fire on world click) |
| `CooldownEnd` | server only | `GetServerTimeNow()` epoch when the lock lifts |

- **Kind-A:** `EquipSlot` stamps `CooldownEnd` inline, then auto-unequips. The client fires optimistically (`fireSkill`) and marks `_expectEcho`, so the silent server stamp never double-fires the veil.
- **Kind-B:** server-owned `Tool.Activated` connections (`_activatedConns`, disconnected on equip/unequip/leave) stamp the end and unarm. Plain tools are never touched.
- **Gates:** server `EquipSlot` returns `ON_COOLDOWN` while locked; client `equipAndClearNew` flashes `CooldownDenied` (layout shake); binds/clicks on cooling slots are silent-dead — the veil is the feedback.
- **Wire key policy** (`Communications.luau`): client-originated writes to the three keys are stripped. Direct server `UpdateMetadata` calls bypass it.
- **Clock domain:** stamps, gates, and the `observeCooldownEnds` FullSync observer all use `Workspace:GetServerTimeNow()` — `os.clock()` is per-machine. The observer anchors true remaining, never full-length.
- **Stacking launder:** `CooldownEnd` is a required stack field here, so cooling↔fresh stacks can't merge (swap-absorb falls back to positional). Gates wipe expired ends (`METADATA_DELETE`) so spent stacks restack.
- **Veils:** `CooldownService` (uuid → end, single RenderStepped Tick) + `cooldown`/`cooldowntext` nodes in the Jailbreak skin prefab, hydrated by both views (nil-safe for other skins).
- **Try it:** Studio play, Conch (Backquote): `cooldown-demo <id> [a|b] [seconds]` (e.g. `cooldown-demo Pickaxe a 5`).
- **Delta vs `client`:** `Interactions/CooldownService.luau`, bind-deny in `Layouts/Shared`, veil blocks in `JailbreakHotbar/*` + `Skins/Jailbreak`, gates/stamps in server `init.luau`, observer in `ClientController.luau`, key policy in `Communications.luau`, `cooldown-demo` in `Debug/ConchCommands.luau`, `CooldownEnd` in shared `Settings.luau` defaults.

## Test Plan

Legacy suites (Lune, client harness, Studio Runner specs) are purged. The
rebuild comes in two phases:

### Phase 1 — data-output tests (now)

One observer-only LocalScript per area (NotifyExample pattern): subscribes to
the bus, peeks live store state, prints structured data lines to Output, then
disables itself — main thread only, observers stay rooted in live state (see
TestingRules). A human evaluates pass/fail from the data. Proven workable:
in-game requires DO reach live modules (the late `LockedSlotsVerify` printed
live token metadata + verdicts) — the no-table-access limit applies to MCP
executes, not to in-game scripts. Prefer direct store peeks over GUI scraping:
GUI can't be trusted for core-functional verification (a correct state can
render wrong and vice versa).

### Phase 2 — automated shape asserts (later)

Same harness plus `expect`-style asserts (error on mismatch) so Output shows
pass/fail without human reading. Enable per playtest; keep tests off the
canon runtime path (no requires from production code).

## Common Pitfalls

1. **`setupDragHandlers()` must run once on init** — not inside `renderInventory()`. The web test tool's drag/drop uses document-level event delegation.
2. **`table.clone` not `Utils.deepCopy`** for flat settings tables — `deepCopy` is for nested item metadata.
3. **`split` always caps at MaxStackSize** regardless of CanStack — this is intentional.
4. **Move never stacks** — use `swap` or `swapStack` with `StackOnSwap = true` if you want to merge.
5. **Static hotbar preserves holes** — `compactHotbar` is a no-op. Only Dynamic compacts.
6. **Sort is descending for rarity** — Special > Mythic > Legendary > ... > Common.
7. **`StackOnSwap` does NOT stack during move** — it applies to swap and swapStack only. This is a common misconception.
8. **Nil values in `updateMetadata`** — In Luau, `{ Key = nil }` creates empty table. Nil values are silently ignored. To delete a key, use the sentinel: `updateMetadata(state, uuid, { Key = CoreStore.METADATA_DELETE })`.
9. **MetadataIndex maintenance** — every `createItem`, `destroyUnplacedItem`, `remove`, and `updateMetadata` must update MetadataIndex.
10. **Dynamic Hotbar slot availability** — The only available slot is the append position (`findEmptyHotbarSlot`). Operations targeting non-append slots are rejected with `DESTINATION_UNAVAILABLE`. Preferred slot is ignored in Dynamic mode. Use `CoreStore.setHotbarType(state, "Dynamic")` to switch types — it auto-compacts the hotbar.
11. **`Fusion.Scope<any>` has no `Hydrate`/`ForPairs`** — `Types.Scope<Constructors> = {Task} & Constructors`, so `Scope<any>` is `any & {Task}` with no Fusion members. Use `Fusion.Scope<typeof(Fusion)>` (as in `HotbarView`, `StorageView`, `SlotView`, `LayoutManager`, `PointerDragService`). Zed `enable_new_solver:true` surfaces this.
12. **Lazy `For` side-effects need `Observer`** — Studio `Fusion` `For` is `timeliness="lazy"`. `scope:ForPairs` that only does `SlotView.Create` + `Parent = hotbarFrame` and ignores the returned table never runs unless observed. Wrap side-effect `For`s with `local f = scope:ForPairs(...); Fusion.peek(f); scope:Observer(f)` as in `HotbarView`/`StorageView`. The 0.3.1 `For` was eager via `updateAll`.
13. **No live property reads as `Computed` fallbacks** — `return slotnumber.TextColor3` inside the `Computed` bound TO `slotnumber.TextColor3` self-perpetuates (once amber, amber forever). Capture once (`local default = inst.Prop`) and return the capture. The codebase already does this (`originalPosition`, `origSize`).
14. **Pushed settings go through `_state` first** — writing atoms directly gets clobbered by the next op's `sync()` (proven live: 10 slots after set-to-4). Funnel: `ClientController.ApplyServerSettings` (overlay onto `_state`, then `sync()` fans out). Same for any future pushed state.
